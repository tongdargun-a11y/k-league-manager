# CLAUDE_EXECUTION.md
# K-LEAGUE MANAGER — Claude 개발 실행 지침

이 문서는 Claude가 실제 프로젝트 코드를 생성·수정할 때 따르는 실행 지침이다. `K-LEAGUE-MANAGER-DESIGN.md`를 먼저 읽고 본 문서와 함께 기준으로 삼는다.

---

## 1. 너의 역할

너는 시니어 풀스택 개발자이자 게임 시스템 엔지니어다. 사용자는 프로그래밍 초보자다. 설명은 한국어로 하고, 명령어는 복사해서 실행할 수 있게 제공한다.

목표는 기획서만 작성하는 것이 아니라 **실행 가능한 K-LEAGUE MANAGER 웹게임을 실제로 개발하는 것**이다.

확정된 제품 사양:
- 실제 K리그 구단 및 선수 중심의 데이터 모델
- 실제 선수 사진 기반 카드(권리 확인된 사진만 사용)
- 게임 내 날짜가 진행되는 시간 시스템
- 경기 중 사용자가 전술 변경 및 선수 교체를 직접 수행
- 싱글 플레이, PC 우선 웹게임, 모바일 반응형
- 첨부 레퍼런스의 다크 네이비·골드 선수 프로필 카드 스타일

## 2. 절대 준수 규칙

1. 한 번에 거대한 코드를 작성하지 말고 작은 실행 단위로 개발한다.
2. 각 단계 종료 시 개발 서버 실행과 검증을 수행한다.
3. 실행하지 않은 코드를 실행했다고 주장하지 않는다.
4. 오류가 있으면 오류 원인, 수정 파일, 수정 내용을 설명한다.
5. 기존 기능을 제거하거나 깨뜨리지 않는다.
6. 버튼은 실제 동작하도록 연결한다. 미구현 버튼은 숨기거나 명확히 비활성화한다.
7. 외부 API, 사진, 엠블럼의 라이선스와 비용을 임의로 가정하지 않는다.
8. 실제 선수 능력치가 공식 공개 데이터가 아니라면 게임용 추정치라고 표시한다.
9. 선수 사진 권한이 없으면 로컬 기본 실루엣을 표시한다. 무단 이미지 핫링크를 하지 않는다.
10. 게임 날짜와 실제 시스템 시간을 혼동하지 않는다.
11. 게임 엔진은 UI 코드와 분리하고 테스트 가능한 순수 함수 중심으로 작성한다.
12. 세이브 데이터는 버전 관리하고 마이그레이션을 고려한다.
13. 사용자가 요청하지 않은 유료 서비스나 클라우드 의존성을 추가하지 않는다.
14. 외부 데이터가 없어도 샘플 데이터로 완전한 MVP 플레이가 가능해야 한다.

## 3. 첫 응답에서 할 일

프로젝트를 시작할 때 다음을 먼저 수행한다.

1. 현재 작업 디렉터리와 파일을 확인한다.
2. `K-LEAGUE-MANAGER-DESIGN.md`를 읽는다.
3. 현재 프로젝트가 비어 있는지, 기존 코드가 있는지 파악한다.
4. 필요한 기술 스택과 폴더 구조를 확정한다.
5. PHASE 0 작업 목록을 제시한다.
6. 사용자에게 불필요한 질문을 반복하지 말고 합리적인 기본값으로 진행한다.
7. 기존 프로젝트가 있다면 덮어쓰기 전에 구조를 분석한다.

## 4. 기술 스택

기본 선택:
- React
- TypeScript
- Vite
- Tailwind CSS
- Zustand
- React Router
- Lucide React
- IndexedDB 저장소(Dexie 등 경량 라이브러리 검토 가능)

라이브러리는 꼭 필요한 것만 설치한다. 버전 충돌이 있으면 안정적인 호환 버전을 선택하고 설치 이유를 설명한다.

## 5. 구현 우선순위

### PHASE 0 — 프로젝트 생성 및 기본 화면

완료해야 할 작업:
- Vite + React + TypeScript 프로젝트 구성
- Tailwind CSS 설정
- 라우팅 설정
- 전역 디자인 토큰 설정
- 공통 레이아웃 및 내비게이션
- 더미 구단·선수 JSON 데이터
- 타입 정의
- 개발 서버 실행

디자인:
- 배경: 딥 네이비
- 강조: 골드
- 카드: 어두운 남색, 얇은 테두리
- 본문: 흰색/회색
- 큰 숫자와 간결한 통계
- 과도한 그라데이션과 장식은 피한다.
- 데스크톱은 좌측 사이드바 또는 상단 메뉴, 모바일은 접이식 메뉴를 사용한다.

### PHASE 1 — MVP 플레이 루프

다음 순서로 구현한다.

#### 1) 새 게임
- 타이틀 화면
- 새 게임
- 세이브 불러오기
- 감독 이름
- 구단 선택
- 초기 세이브 생성

#### 2) 대시보드
- 게임 날짜
- 날짜 진행/정지/속도 선택
- 다음 경기
- 리그 순위 요약
- 최근 경기
- 부상·중요 알림

#### 3) 선수단
- 선수 목록
- 포지션 필터
- OVR 정렬
- 선수 상세 화면
- 사진 없을 때 플레이스홀더
- 출전·득점·도움 기록

#### 4) 선수 프로필 카드
첨부 이미지처럼 세로형 또는 반응형 카드로 만든다.
- 선수 사진
- 이름·국적·포지션·등번호
- OVR
- 통산 출전·득점·도움
- 평균 평점
- 우승·수상 기록
- 시즌별 커리어

기록이 없는 항목은 0 또는 '기록 없음'으로 일관되게 표시한다. 실제 기록과 게임 내 기록은 구분한다.

#### 5) 일정과 순위
- 일정 목록과 월간 달력
- 홈/원정
- 경기 상태
- 승점 계산
- 골득실과 다득점
- 대회별 순위 계산 모듈

대회별 규칙은 설정 데이터로 둔다. 특정 시즌의 K리그 규칙을 코드에 영구 고정하지 않는다.

#### 6) 전술과 라인업
- 포메이션 선택
- 선발 11명
- 벤치
- 포지션 적합도
- 전술 프리셋
- 저장 및 경기 적용

#### 7) 라이브 경기
- 경기 전 라인업 확인
- 경기 타이머
- 경기 이벤트 로그
- 득점·도움·슈팅·파울·경고·부상
- 하프타임
- 선수 교체
- 전술 변경
- 경기 종료 결과
- 기록 자동 반영

경기 엔진은 `src/engine/match` 등에 분리한다. 경기 이벤트 생성, 득점 확률, 선수 평점 계산을 독립 함수로 만들고 테스트한다. 결과를 한 번의 랜덤 추첨으로 결정하지 않는다.

#### 8) 저장/불러오기
- IndexedDB에 세이브 저장
- 자동 저장 시점 정의
- 수동 저장
- 세이브 목록
- 불러오기
- 새 게임
- 데이터 버전 및 마이그레이션

저장 중 새로고침이나 탭 종료가 발생해도 데이터 손상이 최소화되도록 트랜잭션을 활용한다.

## 6. 게임 시간 구현 규칙

게임 시간은 현실 시간과 독립된 상태값으로 둔다.

권장 상태:
- `gameDate`
- `isPaused`
- `speed`
- `lastProcessedDate`
- `pendingEvents`

속도는 예를 들어 일시정지, 하루 단위, 보통, 빠르게로 제공한다. 브라우저의 비활성 탭에서 타이머가 몰아서 실행되지 않게 한다.

하루 처리 함수는 같은 날짜에 중복 실행되어도 결과가 중복되지 않도록 멱등성을 갖춰야 한다.

경기 당일에는 대시보드에서 경기 시작을 명확히 알리고, 경기 중에는 일반 날짜 진행을 중단한다.

## 7. 데이터 모델 구현 규칙

최소 타입:
- Club
- Player
- PlayerAttributes
- PlayerSeasonStats
- PlayerCareerStats
- Manager
- Competition
- Season
- Fixture
- Match
- MatchEvent
- Tactic
- Injury
- SaveGame
- AssetMetadata

모든 엔티티는 안정적인 ID를 사용한다. 이름을 기본 키로 쓰지 않는다.

외부 데이터 필드와 게임 내 수정 필드를 분리한다.
예:
- `source`
- `sourceUpdatedAt`
- `licenseStatus`
- `gameOverride`
- `createdAt`
- `updatedAt`

데이터가 누락된 경우 앱이 중단되지 않도록 유효성 검사와 기본값을 둔다.

## 8. 실제 K리그 데이터 적용 규칙

실제 데이터는 출처와 이용 조건을 확인한 뒤 적용한다.

- 공식 API가 있다고 가정하지 않는다.
- API 키가 필요한 경우 키를 코드에 직접 하드코딩하지 않는다.
- 사용 약관에서 재배포 가능 여부를 확인한다.
- 사진·엠블럼의 권리 상태를 기록한다.
- 무단 크롤링, 무단 핫링크, 저작권 침해 가능성이 있는 데이터 번들 배포를 하지 않는다.
- 실제 데이터 확보 전에는 명확히 표시된 테스트 데이터로 게임을 개발한다.
- CSV/JSON 임포트 기능을 제공해 사용자가 적법하게 확보한 데이터를 가져올 수 있도록 한다.
- 실데이터와 게임용 추정 능력치를 UI에서 혼동하지 않게 한다.

사진 표시 우선순위:
1. 사용 권한 확인된 선수 사진
2. 사용자가 로컬에서 추가한 개인용 사진
3. 기본 포지션 실루엣

배포 빌드에는 권리 확인되지 않은 사진을 포함하지 않는다.

## 9. UI/UX 품질 기준

- 화면마다 공통 헤더와 메뉴 위치를 유지한다.
- 주요 수치와 상태를 한눈에 파악할 수 있게 한다.
- 표는 정렬·필터가 가능해야 한다.
- 선수 카드 클릭 시 상세 프로필로 이동한다.
- 날짜 진행 중에는 진행 상태를 표시한다.
- 경기 중 조작은 명확한 버튼과 확인 절차를 제공한다.
- 모바일에서 표가 깨지면 카드형 레이아웃으로 전환한다.
- 로딩·빈 상태·오류 상태를 디자인한다.
- 키보드 포커스와 색상 대비를 고려한다.

## 10. 테스트 요구사항

각 PHASE 종료 시 아래 항목을 확인한다.

- `npm run dev`로 개발 서버가 실행되는가?
- `npm run build`가 성공하는가?
- TypeScript 오류가 없는가?
- 콘솔에 치명적 오류가 없는가?
- 새 게임을 시작할 수 있는가?
- 하루 진행이 정상 작동하는가?
- 경기 당일 경기가 열리는가?
- 경기 중 교체 및 전술 변경이 반영되는가?
- 득점 시 선수와 구단 통계가 동기화되는가?
- 순위표 승점이 정확한가?
- 저장 후 새로고침해도 세이브가 남아 있는가?
- 사진이 없어도 UI가 깨지지 않는가?

게임 엔진 핵심 로직은 단위 테스트를 작성한다. 예를 들어 승점 계산, OVR 계산, 날짜 이벤트, 경기 기록 반영을 테스트한다.

## 11. 사용자에게 안내하는 방식

사용자가 코딩 초보자라는 점을 고려한다.

명령어를 제시할 때:
1. 터미널을 여는 방법
2. 어느 폴더에서 실행하는지
3. 복사할 명령어
4. 정상 실행 시 보이는 결과
5. 문제가 생겼을 때 확인할 항목

을 순서대로 안내한다.

한 번에 너무 많은 명령을 주지 말고, 중요한 단계에서는 실행 결과를 확인한다. 단, 작업 환경에서 파일을 직접 생성·수정할 수 있다면 사용자가 수동으로 복사해야 하는 불필요한 작업을 만들지 않는다.

## 13. 지금 바로 시작할 작업

먼저 프로젝트 디렉터리를 확인하고 PHASE 0부터 진행한다.

1. 기획서를 확인한다.
2. 현재 작업 환경과 프로젝트 파일을 확인한다.
3. 프로젝트가 없으면 React + TypeScript + Vite 기반으로 생성한다.
4. 디자인 시스템과 기본 레이아웃을 구현한다.
5. 샘플 K리그 구단 및 선수 데이터를 준비한다. 실제 데이터가 아닌 경우 테스트 데이터라고 명확히 표시한다.
6. 대시보드, 선수단, 선수 프로필 화면을 구현한다.
7. 개발 서버와 빌드를 실행해 검증한다.
8. 검증된 상태를 기준으로 PHASE 1의 나머지 기능을 이어간다.

**중요: 설계 설명만 출력하고 멈추지 말 것. 실행 가능한 프로젝트 파일을 실제로 만들고, 단계별로 실행·검증하라.**
